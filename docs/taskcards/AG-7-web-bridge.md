# AG-7 — Отладочный веб-мост чата (тот же протокол страницы поверх HTTP)

Ветка: `feature/ag7-web-bridge` | Борд: Qdrant `oc_plans`, id=`32900697-26dc-4d65-b2d5-aaaa5f493c85`
Зависимости: AG-5/AG-6 (страница агентов и CRUD уже в `main`)

## Статус
**done** (коммиты `3bdb7e6` рефакторинг транспорта + `316ab2a` мост).

## Первоисточник
- Страница чата умела говорить с Java только через встроенный браузер:
  `BridgeBrowser` (`web/chat.html` + `window.colleague(method, json)` + vetoed
  `colleague:` навигация), доставка событий — `window.colleagueEvents([["kind","{json}"],…])`
  (`BridgePushDelivery.pushScript/renderBatch`).
- Снаружи процесс с чатом был недоступен: проверить чат из браузера/Playwright нельзя,
  вся диагностика шла через `System.out` и `diag`-события страницы.
- `ChatPanel` пушил события в один транспорт: `push`/`pushNow` (`ChatPanel.java:910,922`).

## Сделано
1) Красный тест (`WebBridgeTest`, 8, бандл `com.mad.edt.colleague.ui.tests`, без SWT и браузера):
   мост закрыт, пока порт не запрошен (`requestedPort()==0`); сокет только loopback
   (`isLoopback(host)`), токен не короче 32 символов; отдаваемая страница содержит бутстрап
   (`/call`, `/events`, `colleagueEvents`) и токен; запрос без токена → 401 и в панель ничего не
   попадает; вызов с токеном доходит до обработчика как `method + arguments` (кириллица в аргументе
   сохраняется); пуш события приходит в long-poll и читается ровно один раз; пустой полл держит
   запрос (≥50 мс) и отвечает `[]`, не крутя клиент; после `close()` сокет отвечает отказом.
2) `PageTransport` — контракт канала событий страницы (`push`, `pushEvents`), `BridgeBrowser`
   реализует его без изменения поведения (коммит `3bdb7e6`).
3) `WebBridge` (коммит `316ab2a`): HTTP/1.1 прямо на `ServerSocket` (никаких `com.sun.*`, чтобы
   не трогать контракт целевой платформы), привязка к `127.0.0.1`, порт из флага запуска
   `-Dcolleague.webbridge.port=<порт>` (0/нет флага — сокет не открывается вовсе), токен — 32 hex
   из `SecureRandom`, заголовок `x-colleague-token` обязателен на всех путях кроме отдачи самой
   страницы. Отдаётся **тот же** `web/chat.html` из бандла + бутстрап в `<head>`: `window.colleague`
   становится POST `/call` (`{"m":…,"a":…}`), а пуши Java приходят поллом `/events` прямо в
   `window.colleagueEvents` — формат пакетов общий с встроенным мостом (`BridgePushDelivery
   .renderBatch`), поэтому страница не различает транспорты. События, возникшие во время обработки
   вызова, уходят вместе с ответом `/call` — как во встроенном канале.
4) Веер из одной беседы в два транспорта: `ChatPanel.attachMirrorTransport(PageTransport)` +
   `ChatPanel.pageCall(method, arguments)` (перенос вызова в UI-поток панели через `asyncExec`),
   `push`/`pushNow` дублируют события в зеркало; `ColleagueView.openWebBridgeIfAsked()` открывает
   мост в `createPartControl`, `attachWebBridge(panel)` подвешивает вкладку чата (вызовы ведёт
   последняя подключённая вкладка), `dispose()` закрывает порт вместе с видом.

## Критерии приёмки
Без флага — ничего не слушает (`offByDefault`). С флагом: `http://127.0.0.1:<порт>/` отдаёт живую
страницу чата, запросы без токена отбиты (401), страница шлёт вызовы в панель и получает её
события; одна беседа видна одновременно во вкладке EDT и во вкладке браузера.
`WebBridgeTest` 8 зелёные, `mvnw -B clean verify` зелёный (EXIT=0; тесты 265 + 78 + 32).
